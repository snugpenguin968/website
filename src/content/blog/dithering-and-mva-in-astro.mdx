When building a personal website, it is tempting to let data fetching, date formatting, and presentation markup bleed together inside page templates. Over time, small shortcuts turn into tightly coupled components that are hard to test or refactor.

## Why Model–View–Adapter (MVA)?

In **Model–View–Adapter**, the Model layer and View layer never communicate directly. Every piece of data flows through a strictly typed Adapter that translates domain entities into immutable `ViewModel` objects:

```ts
// Thin Astro route page: delegates everything to an Adapter
const vm = await HomePageAdapter.resolve(Astro.url.pathname);
```

Because `.astro` components execute on the server with zero client framework runtime, pairing them with strict MVA gives us:

- **Zero-JS Server Views**: Views only accept `Readonly` ViewModels and render semantic HTML + UnoCSS utility classes.
- **Pure Unit-Testable Domain Logic**: Dithering math, reading-time estimation, and grouping rules run in Vitest without any DOM or Astro runtime.
- **Automated Boundary Checks**: A static import check verifies that Views and Pages never import Models or `astro:content` directly.

## Build-Time Atkinson Dithering

Instead of shipping a multi-megabyte photograph and running canvas pixel manipulation in the browser, the portrait pipeline runs server-side at build time:

1. `PortraitAdapter` decodes `me.png` via `sharp` into an 8-bit grayscale luminance grid.
2. `ditherGrayscaleBitmap` applies configurable error diffusion (`atkinson`, `floyd-steinberg`, or `bayer4x4`).
3. `renderMaskToRgba` produces **true-positive** transparent PNGs for both light mode (dark ink dots for shadows) and dark mode (light ink dots for highlights), avoiding the photographic negative look of naive CSS inversion.

### Configurable by Design

Switching dithering algorithms or toggling the hover-to-reveal photograph takes a single change inside `src/models/site.model.ts`.
